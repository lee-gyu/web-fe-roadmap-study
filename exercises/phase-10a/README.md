# Phase 10a 실습 과제 — 운영 텔레메트리와 장애 분석 리포트

Phase 10a 문서 학습과 병행하는 실습 과제다. 이 Phase의 목표는 관측 도구를 설치하는 것이 아니라, **프로덕션에서 무슨 일이 일어났는지 사후에 질문할 수 있는 증거 체계**를 만들고 그것으로 실제 회귀를 진단해 보는 것이다.

대상 프로젝트는 [Phase 10](../phase-10/README.md)에서 만든 포트폴리오 프로젝트를 권장한다. 없다면 Phase 8의 Next.js 미니 프로젝트나 접근 권한이 있는 실무 저장소를 쓴다. 배포되어 있고 릴리스를 되돌릴 수 있어야 한다.

최종 산출물은 다음 네 묶음이다.

- 관측 설계 노트
- 연결·검증된 텔레메트리 (오류, RUM, 릴리스 식별, 상관관계)
- 운영 대시보드와 SLI/SLO·알림 정의
- 장애 분석 리포트

> **안전 규칙**: 과제 L의 회귀 주입은 staging 또는 소수 트래픽(내부 사용자, 기능 플래그로 격리된 세그먼트)에서만 수행한다. 실사용자에게 영향을 주는 의도적 장애는 이 과제의 목적이 아니다. 실무 저장소를 쓴다면 사전에 팀의 동의를 받는다.

## 1주차 전반 — 텔레메트리 설계와 연결

[10a-1 관측 가능성 멘탈 모델](../../docs/phase-10a/01-observability-mental-model.md)과 병행한다.

### 과제 A. 관측 설계 노트 작성

`docs/observability.md` 또는 같은 목적의 문서를 만든다. **코드를 쓰기 전에 작성한다.**

- [ ] 프로덕션에서 답하고 싶은 질문을 5개 이상 적었다. (예: "결제 실패가 특정 브라우저에 몰려 있는가", "어제 배포가 저사양 기기의 LCP를 악화시켰는가")
- [ ] 각 질문에 필요한 신호를 메트릭·이벤트·트레이스·세션 중에서 지정했다.
- [ ] 각 신호에 붙일 차원을 정의했다. 최소한 릴리스, 정규화된 route, 브라우저, 기기 등급, 네트워크 종류를 포함한다.
- [ ] route 정규화 규칙을 정했다. (`/orders/8f2c-...` → `/orders/:id`)
- [ ] 신호별 샘플링 정책과 그 근거를 적었다.
- [ ] **수집하지 않기로 한 항목과 그 이유**를 적었다. 이 항목이 비어 있으면 설계를 다시 본다.
- [ ] 카디널리티 위험이 있는 차원을 표시하고, 메트릭 태그가 아닌 이벤트 속성으로 둘 것을 명시했다.

### 과제 B. 오류 수집 경로 연결과 검증

각 발생 경로가 **실제로** 수집 엔드포인트에 도달하는지 확인한다. 코드 리뷰로 대신하지 않는다.

개발 환경 전용 진단 화면을 만들어 각 경로를 버튼으로 유발하고, DevTools Network 패널에서 전송을 확인한다.

- [ ] 동기 코드의 예외
- [ ] `unhandledrejection` (await 하지 않은 async 예외)
- [ ] `try/catch`로 잡은 뒤 `reportError()`로 승격한 오류
- [ ] 리소스 로드 실패 (캡처 단계 등록 확인)
- [ ] React error boundary가 잡은 오류 (`onCaughtError`)
- [ ] 어떤 경계도 잡지 못한 오류 (`onUncaughtError`)
- [ ] hydration mismatch 등 React가 복구한 오류 (`onRecoverableError`) — SSR을 쓰는 경우
- [ ] Web Worker 내부 예외 — 사용하는 경우
- [ ] 번들 자체가 로드되지 않는 경우 (인라인 부트 가드)

각 경로에 대해 **도달했는가 / 어떤 컨텍스트가 함께 왔는가**를 표로 기록한다.

### 과제 C. `Script error.` 제거

자산을 CDN이나 별도 도메인에서 서빙한다면 반드시 확인한다.

- [ ] 스크립트 태그에 `crossorigin` 속성이 있다.
- [ ] 자산 응답에 `Access-Control-Allow-Origin`이 있다.
- [ ] 설정 전후로 cross-origin 스크립트의 오류가 실제 메시지와 스택을 갖고 도착하는지 확인했다.

### 과제 D. 릴리스 식별과 source map 파이프라인

- [ ] 빌드 시점에 릴리스 식별자(보통 Git SHA)를 코드에 주입한다.
- [ ] 모든 오류·RUM 이벤트에 릴리스 식별자가 실린다.
- [ ] source map을 생성하되 `sourceMappingURL` 주석이 배포 자산에 남지 않도록 구성했다. (`hidden` 등)
- [ ] source map을 오류 추적 시스템에 업로드하는 단계가 CI에 있다.
- [ ] 배포 디렉터리에서 `.map` 파일이 공개되지 않는다.
- [ ] 프로덕션 빌드에서 의도적 오류를 발생시켜 **원본 파일·줄·함수명**이 복원되는 것을 확인했다.

검증 명령 예시:

```bash
curl -s https://<host>/assets/<main-chunk>.js | tail -c 200 | grep -c sourceMappingURL  # 0
curl -sI https://<host>/assets/<main-chunk>.js.map | head -1                            # 404
```

### 과제 E. 상관관계 경로 실증

- [ ] 세션 ID, 릴리스 ID, 요청 단위 식별자의 수명과 목적을 정의했다.
- [ ] 클라이언트 오류 하나를 골라 **서버 로그의 해당 요청까지 이동**하는 데 성공했다.
- [ ] cross-origin API에 `traceparent`를 붙였다면 preflight 발생 여부와 그 비용을 측정해 기록했다.
- [ ] 또는 `Server-Timing`으로 서버 request id를 클라이언트가 받아 오류 이벤트에 싣는 경로를 구성했다. (`Timing-Allow-Origin` 확인 포함)

### 과제 F. 개인정보와 성능 비용 점검

- [ ] DevTools Network 패널에서 텔레메트리 요청의 payload를 **직접 읽어** 확인했다.
- [ ] URL 쿼리 문자열, 오류 메시지, 요청 헤더에 토큰·이메일·입력값이 포함되지 않는다.
- [ ] 사용자 식별자를 쓴다면 가명 ID를 쓴다.
- [ ] 세션 replay를 쓴다면 입력 필드와 개인정보 영역의 마스킹을 확인했다.
- [ ] SDK를 끈 빌드와 켠 빌드의 LCP·INP를 같은 조건에서 비교해 관측 코드의 비용을 기록했다.

## 1주차 후반 ~ 2주차 전반 — RUM, SLI, 알림

[10a-2 오류·RUM·릴리스 건강도](../../docs/phase-10a/02-errors-rum-and-release-health.md)와 병행한다.

### 과제 G. CWV 수집과 차원 분해

- [ ] LCP·INP·CLS·TTFB를 field에서 수집한다.
- [ ] attribution 정보(LCP 요소와 subpart, INP의 요소·이벤트·구간)를 함께 수집한다.
- [ ] 각 지표에 릴리스·route·기기 등급·네트워크 차원이 붙는다.
- [ ] bfcache 복원(`navigationType`)을 별도로 구분할 수 있다.
- [ ] 대시보드에서 **평균이 아니라 p75**를 본다. 표본 수(n)를 함께 표시한다.
- [ ] 전체 p75와 route별 p75를 비교해, 전체 지표에 묻혀 있던 나쁜 route가 있는지 확인했다.

### 과제 H. 오류 그룹화와 잡음 분리 점검

- [ ] 상위 이슈 5개를 직접 열어 이벤트 샘플이 같은 원인인지 확인했다.
- [ ] 과도한 분할(메시지에 ID·입력값이 섞임, 릴리스마다 새 이슈)이 있는지 판단하고 교정 방향을 적었다.
- [ ] 과도한 병합(한 이슈에 여러 route·원인이 섞임)이 있는지 판단하고 교정 방향을 적었다.
- [ ] 잡음 버킷을 정의했다. (확장 프로그램, 봇, `AbortError`, 네트워크 단절 등)
- [ ] 잡음은 삭제가 아니라 분류다. 각 버킷의 추이를 볼 수 있다.

### 과제 I. SLI와 SLO 정의

SLI를 **2개 이상** 정의한다. 하나는 오류·성공률 계열, 하나는 성능 계열을 권장한다.

각 SLI에 대해 다음을 문서화한다.

- [ ] 분자(좋은 이벤트)의 정의
- [ ] 분모(유효한 이벤트)의 정의 — 무엇을 제외했고 왜 제외했는가
- [ ] 측정 위치(클라이언트/서버/엣지)와 그 선택 이유
- [ ] **측정 편향** — 이 지표가 구조적으로 놓치는 것 (생존 편향, 수집 차단, 표본율)
- [ ] SLO 목표값과 기간
- [ ] 에러 버짓

### 과제 J. 알림 구성

알림을 **2개 이상** 만든다. 하나는 오류·성공률 기반, 하나는 성능 또는 릴리스 건강도 기반.

각 알림에 대해 다음을 기록한다.

- [ ] 발화 조건 (가능하면 긴 창 + 짧은 창의 burn rate 조합)
- [ ] 임계값의 근거 — 어떤 사용자 영향에서 유도했는가
- [ ] 예상되는 오탐 상황과 완화 조건 (최소 표본 수 등)
- [ ] 이 알림을 받은 사람이 **처음 열어 볼 대시보드**
- [ ] 대응 시 확인할 항목 3가지

알림을 절대 건수에 걸지 않았는지 다시 확인한다.

### 과제 K. 릴리스 건강도 판정 규칙

- [ ] 릴리스별 세션 수, fatal 오류율, 핵심 플로우 성공률을 볼 수 있는 대시보드가 있다.
- [ ] 롤백 판정 조건을 사전에 문서화했다. (최소 표본 수 + 이전 릴리스 대비 배수 + regression 여부)
- [ ] `ChunkLoadError` 또는 청크 404의 정상 패턴(배포 직후 증가 후 감소)을 관측하고 기록했다.
- [ ] 이전 릴리스 자산의 보존 정책을 정했다.

## 2주차 후반 — 회귀 주입, 진단, 장애 대응

[10a-3 프로덕션 진단과 장애 대응](../../docs/phase-10a/03-production-diagnostics-and-incidents.md)과 병행한다.

### 과제 L. 통제된 회귀 주입

최소 **2개**를 주입한다. 하나는 오류 계열, 하나는 성능 계열.

오류 계열 예시(하나 선택):

- 특정 조건(특정 route + 특정 데이터 형태)에서만 발생하는 런타임 예외
- API 응답 스키마 변경에 대한 방어 부재로 인한 파싱 실패
- 청크 로드 실패 (이전 자산 삭제 재현)
- error boundary가 잡아 대체 UI만 보이고 보고되지 않는 오류

성능 계열 예시(하나 선택):

- render-blocking 자산 추가
- 상호작용 핸들러에 큰 동기 작업 삽입
- LCP 이미지의 발견 지연 (CSS background로 이동, preload 제거)
- 공간 예약 없는 요소 삽입으로 CLS 유발
- 데이터 응답 지연 주입

기록할 것:

- [ ] 무엇을 어떻게 주입했는가
- [ ] 어떤 세그먼트에만 노출했는가
- [ ] 주입 시각

### 과제 M. 신호에서 출발한 진단

**주입 내용을 보지 않고 신호부터 시작한다.** 가능하면 동료에게 주입을 맡기거나, 주입 후 하루 뒤에 진단을 시작한다.

- [ ] 어떤 신호가 먼저 나타났는가 (알림인가, 대시보드인가, 문의인가)
- [ ] 알림이 울렸는가. 울리지 않았다면 왜인가
- [ ] 시간 축으로 상승 시작 시각을 특정했다
- [ ] 릴리스 축으로 격리를 시도했다
- [ ] 대상 축(route·브라우저·기기·지역)으로 분해했다
- [ ] 계층(클라이언트 / 자산·CDN / API / 서드파티 / 사용자 환경)을 특정했다
- [ ] 성능 회귀라면 subpart·attribution으로 원인 구간을 좁혔다
- [ ] 몇 단계 만에, 몇 분 만에 계층을 특정했는지 기록했다

### 과제 N. 완화와 롤백

- [ ] 완화 수단을 선택하고 그 이유를 기록했다. (롤백 / 기능 플래그 / 자산 되돌리기 / hotfix)
- [ ] 완화를 실행하고 **소요 시간을 측정**했다.
- [ ] 완화 후 신호가 실제로 회복되는 것을 확인했다.
- [ ] 롤백이 불가능하거나 느렸다면 그 이유를 기록했다.
- [ ] 조치를 한 번에 하나씩 적용했다.

### 과제 O. 장애 분석 리포트

`docs/incidents/YYYY-MM-DD-<slug>.md` 형식으로 작성한다.

- [ ] **타임라인**: T0 발생 / T1 최초 신호 / T2 탐지 / T3 대응 시작 / T4 완화 / T5 복구
- [ ] 가장 긴 구간을 지목했다
- [ ] **사용자 영향**: 추정치와 계산 방법, 하한선임을 명시, 교차 확인 출처
- [ ] **증거**: 대시보드 스크린샷, 오류 이슈 링크, 지표 그래프, 관련 배포 diff
- [ ] **기여 요인**: 사람의 실수가 아니라 시스템 관점으로 왜 이 변경이 통과했고, 왜 늦게 발견됐는지까지
- [ ] **재발 방지 조치**: 유입 차단 / 탐지 개선 / 완화 수단 / 결함 제거의 네 계층에서 각각 최소 1개
- [ ] 각 조치에 소유자와 기한이 있다

### 과제 P. 관측 설계 자체에 대한 회고

장애의 원인이 아니라 **관측이 얼마나 잘 작동했는가**를 별도로 회고한다.

- [ ] 탐지가 늦었다면 어떤 신호가 없었는가
- [ ] 알림이 울리지 않았다면 임계·창·분모 중 무엇이 잘못됐는가
- [ ] 진단 중 "이 데이터가 있었으면 좋았을 텐데"라고 느낀 항목은 무엇인가
- [ ] 그 항목을 과제 A의 관측 설계 노트에 반영했다
- [ ] 잡음 때문에 신호를 놓칠 뻔했다면 버킷 분류를 조정했다

## 완성 기준

- [ ] 관측 설계 노트에 답할 질문과 **수집하지 않기로 한 것**이 모두 있다
- [ ] 오류 발생 경로별 도달 여부를 실제 유발로 검증한 표가 있다
- [ ] cross-origin 스크립트의 오류가 실제 메시지와 스택을 갖고 도착한다
- [ ] 릴리스 식별자와 source map으로 스택이 원본 위치로 복원된다
- [ ] 배포 자산에 `sourceMappingURL` 주석과 `.map` 파일이 공개되지 않는다
- [ ] 클라이언트 오류에서 서버 로그로 이동하는 경로를 실증했다
- [ ] 텔레메트리 payload에 개인정보·토큰이 없음을 직접 확인했다
- [ ] 관측 SDK의 성능 비용을 측정해 기록했다
- [ ] CWV가 release·route·기기 차원으로 분해된 대시보드가 있고 p75와 표본 수를 표시한다
- [ ] 상위 오류 이슈의 그룹화 품질을 점검하고 잡음 버킷을 분리했다
- [ ] SLI 2개 이상에 분자·분모·측정 편향이 문서화되어 있다
- [ ] 알림 2개 이상에 임계 근거와 대응 진입점이 있다
- [ ] 릴리스 롤백 판정 조건이 사전에 문서화되어 있다
- [ ] 통제된 회귀 2개 이상을 주입하고 신호부터 출발해 계층을 특정했다
- [ ] 완화 또는 롤백을 실행하고 소요 시간을 측정했다
- [ ] 장애 분석 리포트에 구간별 타임라인·영향 추정·증거·기여 요인이 있다
- [ ] 재발 방지 조치가 네 계층으로 배치되어 있고 **탐지 개선이 최소 1개** 포함된다
- [ ] 관측 설계 자체에 대한 회고 결과가 설계 노트에 반영되어 있다

## 진행 팁

- 코드보다 설계 노트를 먼저 쓴다. "무엇을 답하고 싶은가"가 없으면 수집 항목이 무한정 늘어난다.
- 오류 경로 검증은 반드시 **직접 유발**해서 한다. 가장 자주 새는 곳은 `try/catch`로 삼킨 오류와 React 렌더 경계다.
- source map 파이프라인은 SDK 설치와 같은 작업 단위로 취급한다. 나중으로 미루면 그동안 쌓인 이슈를 아무도 읽지 못한다.
- 대시보드에는 항상 표본 수(n)를 함께 놓는다. 트래픽이 적은 route의 p75 변동을 회귀로 오인하기 쉽다.
- 알림은 적게 만든다. 받았을 때 할 일이 없는 알림은 탐지 능력을 갉아먹는다.
- 회귀 진단은 코드를 열기 전에 시간·릴리스 축을 먼저 자른다. 이 습관 하나가 진단 시간의 대부분을 줄인다.
- 회고에서 원인만 고치고 끝내지 않는다. 다음 장애는 다른 원인으로 오지만, 탐지 능력은 원인과 무관하게 재사용된다.
